# NovaDepot 商用版本 Phase 3：真实业务场景化（2026-04-22）

## 1. 阶段目标
将系统从“功能存在”推进到“真实业务可演示、可理解、可复盘”，形成可直接用于演示、联调、测试的业务场景包。

## 2. 当前业务场景缺口
1. 基线种子（`99-seed-mvp.sql`）仍有历史占位文本与乱码风险，不适合作为高可信业务讲解样本。
2. 商用样本层（`100-seed-business-sample.sql`）已具基础结构，但“业务原因、角色分工、时间分布”不够可复盘。
3. 商品样本缺少“安全库存语义口径”，规格和状态的业务分层不够清晰。
4. 仓库/库位命名、用途、容量规则有数据但无统一解释文档，演示时理解成本高。
5. 客服工单与会话虽可回查，但工单类型、责任人、处理状态链路缺少可截图节点定义。
6. AI 样本已有会话数据，但“问题类型 -> 分析依据 -> 输出建议”的业务闭环说明不足。
7. 缺少统一的“业务一致性校验脚本化口径”，导致演示前准备不稳定。

## 3. 本轮执行范围
1. 优化真实业务样本数据（商品、仓库库位、单据、客服、FAQ、AI）。
2. 打磨 4 套核心业务场景包并提供可截图节点。
3. 增加业务一致性校验口径（仪表盘、库存、工单回查、AI建议、权限边界）。
4. 保持 Docker 本地可执行，不扩展无关功能模块。

## 4. 样本设计口径（Phase 3）

### 4.1 商品样本
1. 分类：饮料食品、日化家清、3C配件、办公耗材。
2. 规格：采用真实包装语义（例：`250ml*24盒`、`70g 500张/包`）。
3. 条码：符合零售形态（13位数字风格）。
4. 安全库存：以 `spec` 中显式标注（例：`安全库存=30件`），并与低库存预警阈值联动说明。
5. 状态：保留 `ACTIVE` 主体样本，补充少量 `DISABLED`/`INACTIVE` 的历史样本用于联调验证（如前端筛选与接口兼容）。

### 4.2 仓库与库位样本
1. 命名规则：`城市-仓别-用途`（例：`成都一号成品仓`）。
2. 库位编码规则：`分区-巷道-层位`（例：`A-01-01`）。
3. 用途区分：`PICK`（拣选）、`STORAGE`（存储）、`STAGING`（暂存）、`RETURN`（退货）。
4. 容量规则：按用途分层（PICK 最小、STAGING 中等、STORAGE 最大）。

### 4.3 单据样本
1. 入库原因：采购到货、临采补货、客户退回入库。
2. 出库原因：销售发货、促销发货、调拨出库。
3. 业务类型：以 `biz_type` + `remark` 形成可读语义。
4. 时间分布：覆盖“今日、近7日、历史完成”，支持仪表盘与回查对照。

### 4.4 客服与 FAQ 样本
1. 工单类型：物流催发、发票变更、质量反馈、退换货咨询。
2. 优先级：`HIGH/MEDIUM/LOW` 按业务紧急度分层。
3. 处理状态：`OPEN/PROCESSING/RESOLVED/CLOSED`。
4. 责任人：显式绑定 `assignee_user_id`。
5. FAQ：`scene + tags` 形成可命中关键词（如“库存不足”“催发”“补货建议”）。

### 4.5 AI 会话样本
1. 问题类型：补货建议、库存风险摘要、客服SOP建议、管理层周报解读。
2. 输出要求：明确“结论 + 依据 + 建议动作”。
3. 业务依据：建议文本显式引用样本 SKU/单据/库存状态。

## 5. 四套核心业务场景包

### 5.1 场景A：仓库日常入库作业链路
1. 适用角色：`warehouse_manager`、`operator`。
2. 起始数据：`IN-SCN-2026042201`（DRAFT）、对应明细与库位。
3. 操作步骤：
   1. 编辑草稿入库单（数量、库位、备注）。
   2. 提交入库单（`DRAFT -> SUBMITTED`）。
   3. 审核入库单（`SUBMITTED -> APPROVED`）。
   4. 过账入库单（`APPROVED -> POSTED`）。
4. 状态变化：单据状态推进、明细 `receivedQty/qualifiedQty` 更新、库存增加、流水新增。
5. 预期结果：详情、列表、库存页、流水页一致。
6. 可截图节点：
   1. 草稿编辑前后对比
   2. 审核通过状态
   3. 过账后库存变化
7. 页面路径：
   1. `/dashboard`
   2. `/wms/inbound`
   3. `/wms/inventory`
8. 常见错误与解释：
   1. 草稿字段缺失导致提交失败：属于表单校验拦截，需补齐商品/库位/数量。
   2. 未审核直接过账失败：状态机要求 `APPROVED` 后才能过账。

### 5.2 场景B：销售出库与低库存预警链路
1. 适用角色：`warehouse_manager`、`admin`。
2. 起始数据：`OUT-SCN-2026042202`（SUBMITTED/APPROVED样本）与低库存SKU。
3. 操作步骤：
   1. 审核出库单（`SUBMITTED -> APPROVED`）。
   2. 发运出库单（`APPROVED -> SHIPPED`）。
   3. 查看低库存告警与库存流水。
4. 状态变化：出库单状态推进、库存扣减、低库存计数变化。
5. 预期结果：库存告警与仪表盘低库存统计一致。
6. 可截图节点：
   1. 发运前状态
   2. 发运后状态
   3. 低库存告警列表
7. 页面路径：
   1. `/wms/outbound`
   2. `/wms/inventory`
   3. `/dashboard`
8. 常见错误与解释：
   1. 发运失败提示库存不足：后端防止负库存，需先补货或调整数量。
   2. 低库存数量与预期不符：按安全库存口径计算，不是单纯固定阈值。

### 5.3 场景C：客服建单与工单回查链路
1. 适用角色：`cs_agent`。
2. 起始数据：客服会话 `CS-SCN-*`、已有工单与 FAQ。
3. 操作步骤：
   1. 会话中发送回复/AI建议。
   2. 创建工单并填写类型语义（在内容与备注体现）。
   3. 更新状态、责任人、备注。
   4. 通过会话ID/工单号回查。
4. 状态变化：工单状态推进（OPEN -> PROCESSING -> RESOLVED/CLOSED）。
5. 预期结果：会话与工单可互相定位，FAQ可命中相关关键词。
6. 可截图节点：
   1. 会话消息与工单联动
   2. 工单状态更新
   3. 回查结果
7. 页面路径：
   1. `/cs/workspace`
   2. `/system/audit-center`（可选）
8. 常见错误与解释：
   1. 未选会话创建工单失败：工单必须绑定有效会话ID。
   2. 状态更新失败：仅允许 `OPEN/PROCESSING/RESOLVED/CLOSED`。

### 5.4 场景D：管理层仪表盘 + AI补货建议链路
1. 适用角色：`admin`、`viewer`（只读验证）。
2. 起始数据：当日入/出库样本、低库存SKU、AI历史会话。
3. 操作步骤：
   1. 打开仪表盘核对 `todayInbound/todayOutbound/lowStockCount`。
   2. 打开 AI 助手提问补货建议。
   3. 对照库存与在途数据验证建议合理性。
4. 状态变化：AI 会话新增，审计新增 `AI/CHAT`。
5. 预期结果：AI建议与真实低库存样本一致，可复盘到 SKU 与单据。
6. 可截图节点：
   1. 仪表盘统计
   2. AI 提问与回复
   3. 对应低库存SKU明细
7. 页面路径：
   1. `/dashboard`
   2. `/ai/enterprise`
   3. `/wms/inventory`
8. 常见错误与解释：
   1. AI 建议过泛：问题描述过短，建议带入目标与周期。
   2. 建议 SKU 无法定位：事实校验失败，需检查样本与库存数据。

## 6. 业务一致性校验口径
1. 仪表盘统计一致性：
   1. `todayInbound` = 今日创建入库单数量。
   2. `todayOutbound` = 今日创建出库单数量。
   3. `lowStockCount` = `available_qty <= 10` 的库存记录数。
2. 库存一致性：
   1. 入库过账后库存应增加；
   2. 出库发运后库存应减少；
   3. `inventory_transactions` 与单据号可对应。
3. 客服回查一致性：
   1. 会话 -> 工单可追溯；
   2. 工单状态、责任人、备注更新后可见。
4. AI一致性：
   1. AI建议文本应包含真实SKU/业务动作；
   2. 不应与库存事实冲突。
5. 权限边界：
   1. `viewer` 仅查看，不可执行写操作；
   2. 关键写操作由 `warehouse_manager/cs_agent/admin` 执行。
