# NovaDepot 未来 3 个 Sprint 落地规划（2026-04-26）

## 1. 规划原则
本规划只面向“让小团队每天能用”的目标，不扩展大而全模块，不继续堆页面，不做无关重构。

约束：
1. 继续保持单租户、本地 Docker 可运行架构。
2. 继续复用现有 WMS、客服、AI、Agent、审计主链路。
3. 每个 Sprint 只解决一类核心问题，优先做闭环，不做大而散的功能铺设。
4. 所有新增能力都必须兼顾角色权限、审计记录、数据可解释性与中文可读性。

---

## 2. Sprint 1：智能体验收口

### 2.1 目标
让 AI 助手、Agent、客服 AI 从“能演示”提升到“真实可帮忙”，减少答非所问、只会给 JSON、只能人工拼回复的问题。

### 2.2 要解决的问题
1. AI 助手对任务型问题识别还不稳定，对开放型问题缺少通用业务回答能力。
2. Agent 任务执行完成后，业务用户仍然难以直接理解结果。
3. 客服 AI 目前更多是建议式，缺少“客户提问后自动识别并自动回复”的最小闭环。
4. AI 与 Agent 虽已打通，但“在哪些页面触发、结果怎么复盘”还不够统一。

### 2.3 本轮范围
1. AI 助手意图识别收口：
   - 强化补货、低库存、异常、日报、工单、SOP 等任务型意图识别。
   - 增加开放型问题的通用业务回答兜底，不要求“什么都懂”，但要做到“不离题、能解释、能追问”。
2. Agent 结果业务化收口：
   - 所有核心任务默认展示“摘要卡 + 表格明细 + 依据 + 建议动作”。
   - 原始 JSON 继续保留，但只作为折叠技术详情。
3. 客服自动 AI 回复最小闭环：
   - 客户消息进入后，先命中 FAQ/规则分类，再生成自动回复。
   - 支持人工接管，不强制全自动。
4. AI/Agent 入口统一：
   - 库存页、客服页、仪表盘页继续只保留一键智能入口，不新增新的独立中心页。

### 2.4 不做什么
1. 不接入付费大模型作为本轮前提。
2. 不做多轮复杂对话编排平台。
3. 不扩展新的业务模块，如采购中心、销售中心、财务中心。
4. 不做全量重做前端设计，只做现有页面内的智能体验收口。

### 2.5 涉及页面
1. `/ai/enterprise`
2. `/agent/center`
3. `/cs/workspace`
4. `/dashboard`
5. `/wms/inventory`

### 2.6 涉及后端模块
1. `modules.ai`
2. `modules.agent`
3. `modules.customerservice`
4. `modules.inventory`
5. `modules.reports`
6. `modules.auditlogs`

### 2.7 涉及数据表
1. `ai_conversations`
2. `ai_messages`
3. `agent_task_runs`
4. `customer_service_sessions`
5. `customer_service_messages`
6. `customer_service_tickets`
7. `faq_knowledge`
8. `inventory`
9. `inventory_transactions`

### 2.8 验收标准
1. AI 助手输入“优先补货顺序是什么”“今天最需要处理什么”“给我一个物流催发 SOP”时，能返回与问题直接相关的结论，不离题。
2. 任务型请求会自动形成 Agent 任务，且返回结果默认是业务化卡片与表格，不要求用户看 JSON。
3. 客服页支持“客户提问 -> 自动 AI 回复 -> 人工继续接管”的页面可见链路。
4. 客服 AI 回复前至少参考 FAQ、分类、优先级、候选回复、SOP 中的一项，不是纯固定模板。
5. 角色权限仍然有效，观察员不能执行写操作，管理员仍能复盘结果与审计链路。

### 2.9 风险与回滚
风险：
1. AI 规则过宽，导致误判任务意图。
2. 自动 AI 回复过于机械，影响客服体验。
3. 结果卡片化过度简化，丢失业务上下文。

回滚：
1. 可关闭 AI -> Agent 自动路由，退回普通 AI 对话链路。
2. 可关闭客服自动回复，只保留 AI 建议模式。
3. 可保留原始 JSON 明细作为兜底展示。

## 3. Sprint 2：流程闭环补强

### 3.1 目标
让单据、工单、审核、备注、历史真正可复盘，支撑团队日常协作，而不是只能“做动作、看结果”。

### 3.2 要解决的问题
1. 入库单、出库单状态机虽可用，但审批、驳回、备注、处理意见链路还不够完整。
2. 客服工单能建能改，但缺少更清晰的处理历史、责任流转与备注语义。
3. 审核分离原则已初步建立，但还需要在更多页面与记录层体现。
4. 首页待办与历史复盘还不够强，业务用户不知道“下一步该处理什么”。

### 3.3 本轮范围
1. 单据闭环补强：
   - 入库/出库增加审核意见、驳回原因、处理备注。
   - 强化“创建 -> 提交 -> 审核 -> 执行 -> 完成/撤回/作废”的状态说明。
2. 工单闭环补强：
   - 工单处理备注、责任人变更、状态变更形成可追踪历史。
   - 明确“自动 AI 回复”和“人工接管”的切换记录。
3. 审核与备注历史：
   - 单据和工单详情页展示结构化历史时间线。
   - 审计中心支持按业务编号直接回查单据和工单。
4. 首页待办最小可用：
   - 管理员看待审核、待异常处理。
   - 仓储运营看待提交、待执行。
   - 客服运营看待回复、待处理工单。

### 3.4 不做什么
1. 不做 BPM/流程引擎平台化。
2. 不引入复杂审批流配置器。
3. 不做跨组织协同或多部门多级审批。
4. 不扩展新的单据类型。

### 3.5 涉及页面
1. `/wms/inbound`
2. `/wms/outbound`
3. `/cs/workspace`
4. `/dashboard`
5. `/system/audit-center`

### 3.6 涉及后端模块
1. `modules.inboundorders`
2. `modules.outboundorders`
3. `modules.customerservice`
4. `modules.auditlogs`
5. `modules.auth`
6. `modules.reports`

### 3.7 涉及数据表
1. `inbound_orders`
2. `inbound_order_items`
3. `outbound_orders`
4. `outbound_order_items`
5. `customer_service_tickets`
6. `customer_service_messages`
7. `audit_logs`
8. `inventory_transactions`

### 3.8 验收标准
1. 入库单/出库单详情中能看到创建、提交、审核、执行相关备注与处理历史。
2. 创建人与审核人不能是同一人，且管理员是唯一审核角色，页面与接口表现一致。
3. 工单状态变更、责任人变更、备注更新在详情里可按时间线查看。
4. 客服页可区分“AI 自动回复过”“人工接管过”“当前责任人是谁”。
5. 首页出现角色化待办区，不新增大页面，仅基于现有首页收口。

### 3.9 风险与回滚
风险：
1. 历史记录展示增加后，页面信息密度过高。
2. 单据状态补强可能影响现有测试脚本与示例数据。
3. 审计与详情双重展示可能造成口径不一致。

回滚：
1. 历史时间线可回退为折叠区展示。
2. 新增备注/意见字段可先做非必填，避免阻塞原流程。
3. 审计中心联动查询可独立关闭，不影响主流程。

## 4. Sprint 3：知识库与 SOP 后台化

### 4.1 目标
把 FAQ、SOP、规则从“写死在代码或页面里”变成可维护资产，让 AI 与客服真正建立持续迭代的知识底座。

### 4.2 要解决的问题
1. 目前 FAQ/SOP/规则分散在种子数据、规则逻辑和页面建议中，维护成本高。
2. 客服自动回复和 AI 回答缺少统一知识来源，后续质量提升空间受限。
3. FAQ 与 SOP 的新增、编辑、停用、优先级管理还不够像后台系统。
4. 规则修改后缺少“影响面”和“回滚”意识。

### 4.3 本轮范围
1. FAQ 后台化补强：
   - 支持问题、答案、场景、优先级、启停状态的维护。
   - 支持面向客服回复与 AI 助手回答的统一引用。
2. SOP 后台化最小可用：
   - 支持主题、适用场景、标准步骤、风险点、复核项维护。
   - 支持客服与仓储页面调用同一份 SOP 数据。
3. 规则维护最小可用：
   - 把部分关键规则外置，例如低库存阈值口径、自动回复优先级、工单分类关键词。
   - 不做复杂规则引擎，只做“可维护配置化”。
4. 知识沉淀闭环：
   - 工单高频问题可沉淀为 FAQ 草稿。
   - 常见处理流程可沉淀为 SOP 草稿。

### 4.4 不做什么
1. 不做语义检索平台或向量数据库。
2. 不做知识图谱。
3. 不接入复杂训练平台或 RAG 平台。
4. 不做多版本发布审批系统。

### 4.5 涉及页面
1. `/cs/workspace`
2. `/cs/faq` 或当前 FAQ 编辑入口所在页
3. `/ai/enterprise`
4. `/agent/center`
5. 现有系统管理或知识维护入口页

### 4.6 涉及后端模块
1. `modules.customerservice`
2. `modules.ai`
3. `modules.agent`
4. `modules.auditlogs`
5. 可能新增轻量 `modules.knowledge` 或在现有客服模块内扩展

### 4.7 涉及数据表
1. `faq_knowledge`
2. `customer_service_tickets`
3. `customer_service_messages`
4. `ai_messages`
5. 预计新增 `sop_knowledge` 或等价表
6. 预计新增轻量规则配置表，或复用现有参数表

### 4.8 验收标准
1. FAQ 能通过后台维护，而不是依赖 SQL 或代码修改。
2. SOP 能通过后台维护，并被客服 AI 与业务任务结果复用。
3. 客服高频问题可生成 FAQ 草稿，人工确认后生效。
4. AI 助手与客服自动回复在命中 FAQ/SOP 时，能说明引用来源。
5. 知识变更有审计记录，可回查谁修改了什么。

### 4.9 风险与回滚
风险：
1. 知识后台化后，编辑自由度过高，可能造成口径混乱。
2. FAQ/SOP 与现有规则逻辑并存，短期内可能出现双口径。
3. 新增知识表后，旧种子数据兼容性需要处理。

回滚：
1. SOP 可先以只读模板形式上线，编辑入口后开。
2. FAQ/SOP 引用失败时，继续回退到规则回复。
3. 新增知识表可不立即替换旧逻辑，先做并行读取。

## 5. 三个 Sprint 的整体顺序说明
1. Sprint 1 先解决“有没有用”的问题，让 AI、Agent、客服先形成最小价值闭环。
2. Sprint 2 再解决“敢不敢天天用”的问题，把流程、审核、备注、历史补全。
3. Sprint 3 最后解决“能不能持续变好”的问题，把 FAQ、SOP、规则沉淀为可维护资产。

这个顺序的原因是：
1. 如果先做知识后台，而前面的 AI/客服/流程还不稳定，知识资产难以真正发挥作用。
2. 如果先做复杂流程，而智能体验还很弱，用户感知不到系统效率提升。
3. 先收口智能体验，再补流程，再沉淀知识，更符合当前代码与商用阶段。

## 6. 建议的进入条件
在进入代码实施前，建议先确认以下事项：
1. Sprint 1 是否接受“规则/免费模式优先，不强依赖付费模型”的前提。
2. Sprint 2 是否坚持“管理员审核、仓储运营执行、客服不参与仓储审核”的职责边界。
3. Sprint 3 是否接受“先 FAQ 后 SOP，再规则配置化”的轻量后台化策略。

## 7. 建议的退出标准
三个 Sprint 全部完成后，NovaDepot 应达到以下状态：
1. 小团队成员按角色登录后，知道自己每天先做什么。
2. AI 能够帮助回答、执行、建议，而不是只做演示。
3. 单据与工单都有完整处理闭环与追溯链路。
4. FAQ、SOP、规则开始从代码逻辑中抽离，形成可运营知识资产。
