# v1.3 Sprint Q4: CSV Import and Pagination Performance

## 1. Executive Summary

Sprint Q4 focuses on CSV import and long-list query stability. It does not add business features and does not change CSV templates, API routes, response shapes, database schema, permissions, frontend behavior, or AI behavior.

The Q4 implementation scope is limited to:

- Batch preloading reference data for product, partner, and inventory CSV imports.
- Preserving row-level error reports, import summaries, skipped row semantics, audit logs, and inventory transaction semantics.
- Replacing Q4-scope MyBatis-Plus `.last("limit ...")` usage with a parameterized mapper method.
- Recording report/export and unpaged list risks without forcing frontend contract changes.

## 2. Current Scan

CSV import findings:

- `ProductsService.parseProductCsv` checked duplicate product codes with one query per CSV row.
- `PartnersService.importCsv` checked duplicate partner codes with one query per CSV row.
- `InventoryService.parseInventoryCsv` checked warehouse, location, product, and inventory with per-row queries.
- Import methods currently return `Map<String,Object>` summaries with `reportId`, `totalRows`, `successRows`, `failedRows`, `skippedRows`, and `errors`.
- Error reports are stored in `import_error_reports` and returned as CSV through existing endpoints.

Pagination and long-list findings:

- `InventoryService.transactions` used `.last("limit 200")`.
- `ProductsService.list`, `PartnersService.list`, and `InventoryService.list` return full arrays to existing frontend callers.
- `ReportsService` uses full `selectList` reads and in-memory aggregation for several reports.
- Report CSV exports build the full CSV body in memory before returning `ResponseEntity<String>`.

## 3. Implemented Q4 Changes

CSV import optimization:

- Product import now preloads existing product codes into a `Map<String, ProductEntity>` before the row loop.
- Partner import now preloads existing partner codes into a `Map<String, PartnerEntity>` before the row loop.
- Inventory import now preloads warehouses, locations, products, and existing inventory rows into maps before the row loop.
- Duplicate rows within the same CSV continue to be treated as duplicates after the first successful insert by updating the in-memory map.
- Inventory import still writes one inventory transaction per successful row, preserving `beforeQty`, `afterQty`, and `changeQty`.

Limit replacement:

- `InventoryTransactionMapper.selectRecent(tenantId, limit)` replaces the raw `.last("limit 200")` path.
- The external `GET /api/v1/inventory/transactions` response remains `ApiResponse<List<InventoryTransactionEntity>>`.

Deferred risks:

- Full-array list endpoints are retained to avoid changing frontend contracts.
- Report aggregation and CSV export memory risks are documented for a later coordinated performance sprint.

## 4. Behavior Preservation

Q4 preserves:

- CSV import endpoints and content types.
- CSV template fields.
- Import summary keys and value semantics.
- Row-level error report format and retrieval endpoints.
- Duplicate SKU / duplicate partner code skipped-row behavior.
- Invalid warehouse, location, product, and quantity error behavior.
- Inventory quantity calculation and transaction recording.
- Existing audit log semantics.
- Existing frontend page behavior.
- Existing permissions and database schema.

## 6. Acceptance Criteria

- Product, partner, and inventory CSV imports no longer perform duplicate/reference lookups per row.
- Inventory import preloads warehouse, location, product, and inventory reference maps before processing rows.
- Row-level errors and summary response shapes remain unchanged.
- `InventoryService.transactions` no longer uses `.last("limit ...")`.
- No frontend, AI, permission, script, migration, or schema changes are introduced.
- All validation commands pass, except any explicitly documented environment-only issue.

## 7. Rollback Strategy

- Roll back product, partner, and inventory import optimizations independently if any import regression appears.
- Roll back the inventory transaction mapper method if the SQL mapping fails in integration validation.
- Keep the documentation entry even if a code optimization is rolled back, with the rollback reason recorded.
- Do not roll back Q1, Q2, or Q3 completed work.
