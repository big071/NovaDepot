# NovaDepot 开发实施计划（可执行版）

## 1. 总开发阶段划分

| 阶段 | 时间建议 | 阶段目标 | Docker 化目标 |
|---|---|---|---|
| Phase 0：基线与脚手架 | 第1周 | 打通前后端基础框架与开发流程 | `backend + mysql + redis` 可一键起；前端可独立跑 |
| Phase 1：MVP 核心闭环 | 第2-4周 | 商品-仓库-库位-库存-入出库-流水-权限-审计 | 引入 `frontend + backend + mysql + redis` 全量 compose 联调 |
| Phase 2：Beta 扩展 | 第5-8周 | 采购/销售/调拨/盘点 + 报表 + 通知 + 客服基础 + Rule AI | 增加初始化脚本与演示数据，支持桌面演示一键启动 |
| Phase 3：商用准备 | 第9-12周 | 多租户预留落地、套餐与计量、AI 增值、稳定性与安全 | 分环境 compose（dev/staging/demo），支持租户级配置 |
| Phase 4：商用上线 | 第13周+ | 小规模商家真实试运行与持续迭代 | 可选共享部署/专属部署，形成标准化运维手册 |

---

## 2. 每个阶段的目标、交付物与模块

## 2.1 Phase 0：基线与脚手架

### 阶段目标
- 建立统一代码规范、目录规范、接口规范、日志规范。
- 打通最小可运行链路：登录 -> 访问受保护 API -> 页面展示。

### 交付物
- 前端与后端脚手架工程（已完成基础）。
- `docker-compose` 本地运行说明。
- 基础文档（PRD/IA/API/DB/架构/设计系统）。

### 建议完成模块
- auth、users（基础读取）
- settings（基础读取）
- health check、swagger

### 前端任务
- 登录页与后台主框架。
- API 客户端封装、鉴权拦截。

### 后端任务
- Spring Security + JWT + RBAC 骨架。
- 全局异常、统一返回、参数校验、审计切面基础。

### 数据库任务
- `tenants/users/roles/permissions` 等基础表建表。
- seed 数据（管理员、基础权限）。

### 测试任务
- 登录流程冒烟测试。
- 核心接口 Postman 集合。

### 风险点
- 规范没锁死导致后期重构成本高。
- Docker 环境和本地环境配置漂移。

---

## 2.2 Phase 1：MVP 核心闭环（最小上线）

### 阶段目标
- 完成“库存核心闭环”：商品 + 仓库 + 库位 + 库存 + 入库 + 出库 + 库存流水 + 仪表盘。

### 交付物
- 可演示的业务主链路。
- 核心接口与页面可联动。
- Docker 一键启动演示包。

### 建议完成模块
- products, warehouses, locations
- inventory, inventory-transactions
- inbound-orders, outbound-orders
- reports（dashboard 基础）
- audit-logs（关键动作）

### 前端任务
- 商品列表页
- 仓库/库位管理页
- 库存列表/流水页
- 入库单列表与操作页
- 出库单列表与操作页
- 仪表盘页（统计卡 + 趋势图）

### 后端任务
- 入库/出库状态流转与库存增减规则。
- 流水强制写入。
- 低库存预警接口。

### 数据库任务
- WMS 核心表与索引优化。
- 幂等字段（request_id）策略。

### 测试任务
- 单据状态机测试。
- 并发库存扣减边界测试。
- SQL 索引与慢查询检查。

### 风险点
- 库存准确性与并发一致性。
- 状态机跳转约束遗漏。

---

## 2.3 Phase 2：Beta 扩展

### 阶段目标
- 在核心闭环上扩展轻 ERP、智能客服基础、免费 AI 能力。

### 交付物
- Beta 可试用版本（内部/种子用户）。
- 业务流程覆盖采购、销售、调拨、盘点、客服。

### 建议完成模块
- purchase-orders, sales-orders
- transfer-orders, stocktake-orders
- suppliers, customers
- notifications
- customer-service（会话/消息/转接/FAQ/工单基础）
- ai（mock + rule provider）

### 前端任务
- 采购/销售列表与详情
- 调拨/盘点页面
- 客服工作台（三栏）
- AI 助手页（会话 + 建议卡片）
- 报表中心（库存/采购/销售/客服）

### 后端任务
- 采购/销售与库存联动。
- 客服会话与工单升级基础流程。
- AI Provider 抽象层与 rule 路由。

### 数据库任务
- ERP 与客服表补齐。
- FAQ/规则/AI 会话消息落库。

### 测试任务
- 端到端流程测试（采购到入库、销售到出库、客服转工单）。
- 权限测试（不同角色菜单与接口）。

### 风险点
- 模块快速增多导致耦合升高。
- 客服与 AI 规则误判影响体验。

---

## 2.4 Phase 3：商用准备

### 阶段目标
- 完成多租户与商业化基础能力，保证可收费、可运营、可控成本。

### 交付物
- 多租户兼容策略落地（先行级隔离）。
- 套餐/订阅/计量模型。
- AI 增值包开关与配额控制。

### 建议完成模块
- tenant settings / tenant features（新增）
- plans / subscriptions / usage meter（新增）
- billing（最小账单明细）
- platform ops（租户管理后台）

### 前端任务
- 租户管理页（平台端）
- 套餐与订阅页
- 用量统计页（API/AI/会话）

### 后端任务
- 租户级配置读取与缓存。
- 配额检查拦截（用户数、单据量、AI调用量）。
- 计量任务（日统计落库）。

### 数据库任务
- 新增商业化表：`plans`, `plan_features`, `tenant_subscriptions`, `usage_meter_daily`, `billing_*`。
- 租户配置表：`tenant_settings`, `tenant_features`。

### 测试任务
- 串租测试与权限越权测试。
- 配额超限行为测试。
- 计费对账测试。

### 风险点
- 多租户隔离漏洞风险。
- AI 成本失控风险。

---

## 2.5 Phase 4：商用上线与运维

### 阶段目标
- 小规模真实商家上线，建立稳定运营机制。

### 交付物
- 上线 SOP、回滚方案、监控告警、客户支持流程。
- 每周迭代节奏与版本发布机制。

### 建议完成模块
- 监控告警与日志检索
- 数据备份恢复
- SLA 看板
- 安全基线（限流、审计、敏感脱敏）

### 前端任务
- 运营后台可观测页
- 客诉与工单SLA可视化

### 后端任务
- 限流与熔断策略。
- 灰度开关与配置中心增强。

### 数据库任务
- 备份策略与恢复演练。
- 冷热分层与归档策略。

### 测试任务
- 压测、稳定性测试、容灾演练。

### 风险点
- 实际业务峰值超出预期。
- 运维自动化不足导致线上操作风险。

## 3. MVP / Beta / 商用版范围

## 3.1 MVP 最小上线范围
- 登录、权限、角色
- 商品、仓库、库位
- 库存查询、库存流水
- 入库创建/审核/入账
- 出库创建/审核/发运
- 低库存预警
- 仪表盘基础统计
- Docker 一键演示环境

## 3.2 Beta 测试范围
- 采购、销售、调拨、盘点
- 供应商、客户
- 通知、审计、导入导出基础
- AI（mock/rule）
- 智能客服基础（会话+消息+转接+FAQ+工单）

## 3.3 商用版上线范围
- 多租户（行级隔离 + 租户配置）
- 套餐订阅与用量计量
- AI 增值包与配额
- 客服绩效与满意度完整闭环
- 运营后台与风控策略

## A. 适合 Solo 开发者路线

### 建议路线（12周）
1. 周1-2：Phase0 + MVP 基础骨架。
2. 周3-5：库存核心闭环（最关键）。
3. 周6-8：ERP 轻量扩展（采购/销售优先）。
4. 周9-10：AI + 客服基础。
5. 周11-12：多租户预留 + 商业化最小模型。

### Solo 关键原则
- 先可运行，再优化。
- 每周必须有可演示版本。
- 避免一次引入过多复杂技术（消息队列、微服务先不做）。

---

## B. 适合小团队路线

### 推荐分工（3-5人）
- FE（1-2人）：后台框架、业务页面、图表与客服工作台。
- BE（2人）：WMS/ERP 业务服务、权限、AI/客服。
- 兼测/运维（1人可兼职）：测试脚本、compose、演示环境维护。

### 并行策略
- 前端先用 mock 数据并行推进。
- 后端按模块提供稳定 API 合同。
- 每周固定一次 API 对齐评审。

---

## C. 每周开发节奏建议（Vibe Coding 友好）

1. 周一：明确本周目标（不超过3个）。
2. 周二-周四：专注实现与联调。
3. 周五：回归测试 + 文档更新 + 演示录屏。
4. 每天：保留 30 分钟做“文档/脚本/规范”维护，防止技术债。

---

## D. 哪些功能必须先做

1. 权限认证与租户上下文（即使当前单租户）。
2. 库存闭环与库存流水。
3. 单据状态机（入/出库、采购/销售）。
4. 审计日志与基础报表。
5. Docker Compose 一键运行与演示数据。

---

## E. 哪些功能可以延后

1. 高级报表导出与复杂 BI。
2. 多渠道客服接入（先做站内）。
3. 多语言与国际化。
4. 全自动化计费对账。
5. 企业级专属部署自动化。

---

## F. 哪些功能绝对不要一开始做太重

1. 一开始就微服务化。
2. 一开始就接复杂 paid LLM 全链路。
3. 一开始就做过深规则引擎 DSL。
4. 一开始就上复杂工作流引擎。
5. 一开始就做全量 BI 数据仓库。

建议：先“模块化单体 + 清晰边界 + 可替换抽象”，再演进。

## 每阶段 Docker 化落地目标（必须达成）

| 阶段 | Compose 编排目标 | 验收标准 |
|---|---|---|
| Phase0 | `backend + mysql + redis` | 后端可启动，Swagger可访问 |
| Phase1 | `frontend + backend + mysql + redis` | 核心库存闭环可演示 |
| Phase2 | 增加初始化数据与演示脚本 | Beta 全流程可演示 |
| Phase3 | 分环境配置（dev/demo/staging） | 可切租户模式与套餐开关 |
| Phase4 | 生产化部署模板（共享/专属） | 上线回滚与监控告警可执行 |

---

## 本轮建议的“立即执行清单”（下一周）

1. 完成 MVP 核心接口回归用例（库存与单据）。
2. 将客服基础接口补齐到 Beta 可用级别。
3. 增加租户商业化运行配置开关读取（不改核心流程）。
4. 统一前后端演示脚本：本地一键启动 + 演示账号。
