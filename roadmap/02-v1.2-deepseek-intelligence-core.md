# v1.2 —— DeepSeek 仓库智能大脑

> STATUS: PLANNED
> 预估周期：8-12 周
> 前置条件：v1.1 进销存闭环完成（购销数据是 AI 理解仓库的必要上下文）

---

## 1. 版本定位

**把 DeepSeek 从"占位符"升级为 NovaDepot 的真正智能核心，让 AI 从"关键词回复机器人"变成"懂仓库物流的数字专家"。**

### v1.0 AI 为什么"笨"

| 问题 | 根因 |
|------|------|
| 只会关键词匹配 | `RuleAiProvider` 是 8 条 if-else，问法稍变就 miss |
| 回答像模板填空 | 所有回复都是固定模板 + SQL 聚合结果拼接 |
| 不理解上下文 | 问"那个供应商的货到了吗"——不知道"那个"指谁 |
| 不会主动查数据 | 只能走预定义的规则查询，不能根据对话动态决定查什么 |
| 多轮对话记忆弱 | 每轮独立处理，不记得上一轮说了什么 |
| DeepSeek 根本没接入 | `DeepSeekChatAiProvider` 是纯占位符，返回固定字符串 |
| 没有流式输出 | 用户等 2-8 秒看到完整回复，体验像"系统卡了" |
| 不会调用工具 | AI 无法主动查询库存/订单/客服工单——只能等 RuleProvider 喂数据 |

### v1.2 目标对比

| 维度 | v1.0 (RuleAiProvider) | v1.2 (DeepSeek Intelligence) |
|------|----------------------|------------------------------|
| 理解方式 | 关键词匹配 | 自然语言语义理解 |
| 回答来源 | 固定模板 + SQL 拼装 | LLM 推理 + 工具查询 + 知识库引用 |
| 上下文 | 单轮无记忆 | 多轮对话上下文保持 |
| 数据能力 | 仅库存/库存流水 2 张表 | 库存 + 采购 + 销售 + 工单 + 知识库全链路 |
| 主动性 | 被动响应 | 可主动发现异常 + 推送预警 |
| 输出体验 | 一次性返回全文 | 流式打字机输出 |
| 底层引擎 | if-else 规则 | DeepSeek API（HTTP 调用） |

## 2. 核心矛盾

| 矛盾 | 现状 | 目标 |
|------|------|------|
| AI 不懂仓库业务 | 关键词匹配，覆盖率 < 30% | DeepSeek 理解自然语言仓库问题，覆盖率 > 90% |
| DeepSeek 从未对接 | Provider 是占位符，无 HTTP 调用 | 真实 HTTP API 集成 + 流式输出 + 降级策略 |
| AI 不能主动查数据 | 只能走预定义 SQL 规则 | Function Calling：AI 自主决定查询哪些业务数据 |
| 多轮对话无记忆 | 每轮独立处理 | 会话级上下文窗口 + 历史消息管理 |
| 没有运营可视性 | 无报表/通知/预警 | 报表中心 + 通知中心 + Agent 定时巡检 |

## 3. 功能范围

### 3.1 DeepSeek 真实接入 ⚠️ 核心改造

> **目标**：用 DeepSeek API 替换占位符，实现真正的 LLM 推理。

#### 3.1.1 HTTP 客户端集成

| 能力 | 说明 |
|------|------|
| HTTP 调用 | 使用 Spring Boot `RestClient` 或 OkHttp 调用 DeepSeek Chat Completions API |
| 端点 | `https://api.deepseek.com/v1/chat/completions` |
| 认证 | Bearer Token，从 `app.ai.deepseek.api-key` 环境变量读取 |
| 模型 | `deepseek-chat`（默认）；管理员可切换 `deepseek-reasoner` |
| 超时 | 连接超时 5s，读取超时 30s |
| 重试 | 失败后自动重试 1 次（间隔 1s） |
| 用量日志 | 每次调用记录 token 消耗 + 延迟，写入 `ai_usage_logs` 表 |

#### 3.1.2 System Prompt 领域注入

> **核心**：让 DeepSeek 知道自己在一个仓库管理系统里，理解业务上下文。

```text
## 角色
你是 NovaDepot 仓库智能助手，服务于一个仓库管理团队（3-15 人）。
你了解仓库管理、库存、采购、销售、客服工单等业务。

## 当前上下文
- 当前时间：{currentTime}
- 当前用户：{userName}，角色：{role}
- 仓库：{warehouseName}，SKU 总数：{totalSku}，库存条目数：{totalItems}

## 能力边界
- 你可以查询系统内的库存、采购单、销售单、工单等数据
- 你可以给出业务建议，但最终决策由人工确认
- 如果你不确定某个数据是否存在，请使用工具函数查询
- 所有回答基于系统数据，不凭空编造

## 回答风格
- 简洁、专业、结构化
- 数据用表格或列表展示
- 不确定时明确说明，不做猜测
```

#### 3.1.3 降级策略

```
用户提问
  → AiService 路由到 DeepSeekChatAiProvider
  → DeepSeek API 调用
  ├─ 成功（2s 内）→ 流式返回
  ├─ 超时（30s）→ 降级到 RuleAiProvider + 提示 "DeepSeek 响应较慢，已切换为规则引擎"
  ├─ 4xx 错误 → 降级到 RuleAiProvider
  ├─ 5xx 错误 → 重试 1 次 → 仍失败则降级
  └─ 网络不可达 → 降级到 RuleAiProvider
```

### 3.2 流式输出（SSE）⚠️ 核心改造

> **目标**：用户发送消息后，AI 逐字输出，体验像聊天应用而非"等结果"。

| 能力 | 说明 |
|------|------|
| 后端 SSE 端点 | `POST /api/v1/ai/chat/stream` 返回 `text/event-stream` |
| 前端 EventSource | 使用 `EventSource` 或 `fetch` + `ReadableStream` 消费 SSE |
| 打字机渲染 | 前端逐字符追加到消息气泡，不阻塞 UI |
| 中断支持 | 用户可点击"停止生成"中断流式输出 |
| 流式降级 | SSE 不可用时（如某些代理环境），降级为非流式请求 |

**SSE 事件格式**：
```
event: token
data: {"content": "当前"}

event: token  
data: {"content": "库存"}

event: done
data: {"conversationId": 42, "tokens": 156}
```

### 3.3 Function Calling（工具调用）⚠️ 核心改造

> **目标**：让 AI 能自主决定查询哪些业务数据，而非仅走预定义规则。

#### 3.3.1 工具函数清单

| 工具名 | 功能 | 输入参数 | 返回数据 |
|--------|------|----------|----------|
| `query_inventory` | 查询库存 | `productName?`, `warehouseId?`, `lowStock?` | 库存列表（产品/仓库/数量/可用数） |
| `query_inbound` | 查询入库单 | `status?`, `dateFrom?`, `dateTo?`, `partnerName?` | 入库单列表 |
| `query_outbound` | 查询出库单 | `status?`, `dateFrom?`, `dateTo?`, `partnerName?` | 出库单列表 |
| `query_purchase` | 查询采购单 | `status?`, `dateFrom?`, `dateTo?`, `partnerName?` | 采购单列表 |
| `query_sale` | 查询销售单 | `status?`, `dateFrom?`, `dateTo?`, `partnerName?` | 销售单列表 |
| `query_tickets` | 查询客服工单 | `status?`, `assignee?`, `dateFrom?` | 工单列表 |
| `query_product` | 查询产品 | `name?`, `sku?`, `category?` | 产品详情 |
| `query_partner` | 查询往来单位 | `name?`, `type?` | 往来单位信息 |
| `get_inventory_stats` | 库存统计概览 | `warehouseId?` | 总SKU/总数量/低库存数/滞销数 |
| `get_daily_report` | 今日运营概览 | 无 | 今日入库/出库/新增工单/应收应付汇总 |

#### 3.3.2 Function Calling 流程

```
用户："最近一周有哪些采购单还没到货？"
  → DeepSeek 理解意图：查询最近7天状态为CONFIRMED/PARTIAL的采购单
  → DeepSeek 生成 function_call: query_purchase(status="CONFIRMED,PARTIAL_RECEIVED", dateFrom="7天前")
  → AiService 执行 query_purchase → 返回数据
  → DeepSeek 用数据生成自然语言回复："最近一周有3笔采购单尚未完全到货：\n1. PO-20260420-001..."
```

**OpenAI-compatible Function Calling 格式**（DeepSeek 兼容）：
```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "query_inventory",
        "description": "查询当前库存情况，可按产品名称、仓库、是否低库存筛选",
        "parameters": {
          "type": "object",
          "properties": {
            "productName": {"type": "string", "description": "产品名称（模糊匹配）"},
            "warehouseId": {"type": "integer", "description": "仓库ID"},
            "lowStock": {"type": "boolean", "description": "是否仅查询低库存商品"}
          }
        }
      }
    }
  ]
}
```

### 3.4 多轮对话上下文

| 能力 | 说明 |
|------|------|
| 会话历史 | 每个 conversation 保留最近 20 轮对话（40 条消息） |
| 上下文窗口 | 将历史消息注入 DeepSeek 请求的 `messages` 数组 |
| 上下文压缩 | 超过 20 轮后，对早期消息做摘要压缩（调用 DeepSeek 生成摘要） |
| 会话切换 | 用户可新建会话、切换历史会话 |
| 会话过期 | 24 小时无活动自动归档 |

### 3.5 Agent 定时巡检 + 主动预警 ⚠️ 保留原规划

> **前置**：Function Calling 已就绪，Agent 可以用同样的工具函数做巡检。

| 能力 | 说明 |
|------|------|
| 低库存巡检 | 每小时检查所有产品库存，低于阈值自动生成预警通知 |
| 单据超时预警 | 待审核超过 24h / 待执行超过 48h 的单据自动预警 |
| 工单超时预警 | 待处理工单超过 4h 自动预警 |
| 异常检测 | 库存为负 / 单次变动超过阈值 → 自动告警 |
| 推送方式 | 站内通知中心 |

**实现方式**：Spring `@Scheduled` 定时任务 → 调用 `AiService` 的工具函数查询 → 生成通知。

## 7. 配置项

```yaml
# application.yml 新增/修改
app:
  ai:
    deepseek:
      enabled: true                    # 默认启用
      api-key: ${DEEPSEEK_API_KEY}     # 环境变量
      chat-model: deepseek-chat
      reasoner-model: deepseek-reasoner
      timeout-seconds: 30
      max-retries: 1
      fallback-to-rule: true           # 降级到 RuleAiProvider
    streaming:
      enabled: true
      buffer-size: 1024
    context:
      max-history-rounds: 20           # 多轮对话保留轮数
      session-ttl-hours: 24            # 会话过期时间
    tools:
      max-calls-per-turn: 5            # 单轮对话最多调用工具次数
  agent:
    patrol:
      low-stock-cron: "0 0 * * * ?"    # 每小时
      overdue-order-cron: "0 0 */4 * * ?"  # 每4小时
  audit:
    retention-days: 90                 # 审计日志保留天数
```

## 8. Provider 架构升级对比

```
v1.0 架构：
  用户提问 → AiService → RuleAiProvider (if-else 关键词匹配)
                └── (DeepSeekChatAiProvider 是占位符，从未调用)

v1.2 架构：
  用户提问 → AiService → DeepSeekChatAiProvider
                ├── 构建 System Prompt（注入当前仓库上下文）
                ├── 构建 messages（历史对话 + 当前问题）
                ├── 注册 tools（10 个业务查询函数）
                ├── POST https://api.deepseek.com/v1/chat/completions
                ├── [如返回 function_call] → 执行工具函数 → 再次调用 DeepSeek 生成最终回复
                ├── [流式模式] → SSE 逐 token 推送
                └── [降级] → RuleAiProvider（兜底）
```

## 10. 验收标准

### DeepSeek 智能核心
1. DeepSeek API 真实调用成功，能理解"最近一周入库了多少货"这类自然语言问题。
2. AI 回答能主动查询库存/采购/销售/工单数据（Function Calling 正常执行）。
3. 流式输出逐字展示，体验流畅，支持中断。
4. 多轮对话能记住上下文（"刚才说的那个供应商"能被正确理解）。
5. System Prompt 正确注入当前仓库/用户上下文。
6. DeepSeek 不可用时自动降级到 RuleAiProvider，不中断服务。

### 运营工具
7. 报表中心提供 4 类报表 + 图表 + CSV 导出。
8. 通知中心可见历史通知，标记已读，点击跳转关联页面。
9. Agent 定时巡检自动发现低库存/超时单据并推送通知。

### 前端体验
10. AI 对话页面支持流式打字机效果 + 工具调用过程可视化。
11. 骨架屏在 DataTable/Dashboard 加载时正确显示。
12. API 错误信息展示中文友好文案。
13. 打印模板在所有单据详情页可用。

### 稳定性
14. 现有 E2E 测试不回退。
15. Docker 一键启动不受影响。
16. 审计日志按时清理，不无限增长。

4. 不做邮件/短信/企微等外部推送渠道。
5. 不做自定义报表设计器 / BI 分析 / 实时大屏。
6. 不做独立移动端 App / 离线模式 / 响应式适配。
7. 不做通知订阅偏好配置。
8. 不做多租户 / 计费（留到 v2.0）。

## 12. 风险与应对

| 风险 | 应对 |
|------|------|
| DeepSeek API 不稳定/限流 | 自动降级 RuleAiProvider；用量日志追踪；API Key 多备 |
| Function Calling 不准确 | 先用小范围工具测试，逐步扩展；每轮最多调用 5 次防无限循环 |
| 流式输出在代理环境下不可用 | 检测 SSE 不可用时降级为非流式 |
| System Prompt 被 LLM 忽略/绕开 | 回复中强制展示引用数据来源（工具查询结果原文） |
| DeepSeek 回答内容不可控（编造数据） | 所有数据类回答必须来源于工具查询结果，AI 不允许凭空生成数字 |
| token 成本不可控 | 用量日志 + 前端展示消耗；单次调用上限 4096 tokens |
| Agent 定时任务增加 DB 负载 | 低频巡检（每小时/每4小时），使用只读从库查询 |
| 上下文过长导致 token 浪费 | max-history-rounds=20，超限自动摘要压缩 |

### 回滚策略
- AI Provider 可一键切回 RuleAiProvider（管理后台配置）。
- Agent 定时巡检可关闭。
- 通知中心独立模块，关闭不影响主链路。
- 流式输出可关闭，降级为非流式。
