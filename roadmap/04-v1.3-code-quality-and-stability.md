# v1.3 —— Code Quality & Stability

> STATUS: READY FOR RELEASE
> 预估周期：4-6 周
> 前置条件：v1.2 DeepSeek 智能核心已完成（AI Provider / 流式输出 / Function Calling / Agent 巡检 / 通知中心 / 报表中心 / 审计日志清理）

---

## 1. 版本定位

**v1.2 迭代堆积了大量功能代码，现在需要一个"瘦身整理"阶段。不新增任何业务功能，只做质量提升和稳定性加固。**

### 为什么 v1.3 必须是"不写新功能"的版本

| 问题 | 根因 | 后果 |
|------|------|------|
| 后端 Service 类体量过大 | 4 个版本功能持续追加，Service 方法 30+ 个 | 单类 800+ 行，难以维护和测试 |
| 前端组件耦合度高 | 大量"神器组件"(God Component)，一个 .vue 文件 500+ 行 | 改一处理解全部，回归风险高 |
| 测试覆盖不均衡 | E2E 10 条覆盖主链路，但单元测试几乎为零 | 重构无安全网，不敢改代码 |
| 重复代码/工具函数散落 | 多处 `formatDate` / `parseResponse` / `buildPageQuery` 各自实现 | 修改一处遗漏多处，行为不一致 |
| TypeScript 类型宽松 | `any` 随处可见，类型守卫缺失 | IDE 智能提示弱，运行时才发现类型错误 |
| 错误处理不统一 | 有的抛 500、有的吞异常、有的返回空列表 | 用户体验不一致，排查困难 |
| 日志混乱 | `System.out.println` + SLF4J 混用，级别随意 | 生产问题无法快速定位 |
| Docker 镜像体积膨胀 | 多层构建未优化，基础镜像未锁定版本 | 拉取慢、启动慢、占用磁盘 |
| CI 流水线不稳定 | 偶发性 MySQL/Redis 连接超时、npm install flaky | 合并受阻，团队效率下降 |

### v1.3 目标对比

| 维度 | v1.2 (现状) | v1.3 (目标) |
|------|-------------|-------------|
| 后端 Service 单类行数 | 平均 400-800 行 | ≤ 300 行 / 类，单一职责拆分 |
| 前端组件单文件行数 | 多组件 400-600 行 | ≤ 250 行 / 组件 |
| 后端单元测试覆盖率 | ≈ 0% | 核心 Service ≥ 60% |
| 前端组件测试 | ≈ 0 | 通用组件 ≥ 50% |
| TypeScript `any` 数量 | 未统计，大量存在 | 消除所有可推断的 `any`，`strict: true` 零错误 |
| 重复代码 | 多处工具函数重复 | 统一到 `shared/utils`，单一来源 |
| 错误处理 | 不一致 | `GlobalExceptionHandler` 全覆盖 + 业务异常统一枚举 |
| 日志规范 | SLF4J + System.out 混用 | 全部 SLF4J，按级别分层，无 System.out |
| Docker 镜像大小 | 未优化 | 前端 < 50MB，后端 < 300MB |
| CI 稳定性 | 偶发失败需重试 | 连续 10 次全绿不重试 |
| E2E 覆盖 | 10 条主链路 | ≥ 25 条（新增角色边界、并发、边界值） |

## 2. 核心原则（不可妥协）

1. **不新增任何业务功能** — 如有业务需求，推迟到 v1.4 或 v2.0。
2. **不改变任何对外 API 契约** — 请求/响应格式、HTTP 状态码语义、路由路径、权限规则必须保持 v1.2 行为不变。
3. **不改变数据库 Schema** — 不新增/删除/修改表结构、列、索引、外键。
4. **不改变配置文件格式和环境变量名** — 只允许添加新配置项（带默认值），不允许删除或重命名已有项。
5. **所有变更必须有自动化测试保护** — 重构前先补测试地基，重构后跑全量测试门禁。
6. **一次只重构一个模块** — 不允许跨模块大规模同时改动。

## 3. 功能范围

### 3.1 后端重构（第 1-3 周）

#### 3.1.1 Service 层拆分解耦

> **目标**：每个 Service 类 ≤ 300 行，单一职责，可独立测试。

| 现状问题 | 重构方案 |
|----------|----------|
| `InventoryService` 包含入库+出库+盘点+库存查询+流水，500+ 行 | 拆为 `InventoryQueryService` / `InboundService` / `OutboundService` / `StocktakeService` |
| `AiService` 包含流式+非流式+Function Calling+会话管理+Provider 路由，600+ 行 | 拆为 `AiChatService` / `AiStreamService` / `AiToolService` / `AiSessionService` |
| `TicketService` 包含工单+会话+消息+沉淀知识，400+ 行 | 拆为 `TicketService` / `TicketMessageService` / `TicketKnowledgeService` |
| ERP 购销 Service 混合在一个类 | 拆为 `PurchaseService` / `SalesService` / `FinanceService` |

**拆分规则**：
- 读/写分离：查询类方法抽到独立的 `*QueryService`
- 领域分离：不同业务实体（入库/出库）分到不同 Service
- 横切关注点分离：审计/通知/日志用 AOP 或事件解耦

#### 3.1.2 Controller 层规范化

| 现状问题 | 重构方案 |
|----------|----------|
| 部分 Controller 包含业务逻辑（参数校验后的拼装、转换） | 所有业务逻辑下沉到 Service，Controller 只做参数接收+调用+返回 |
| 返回值不统一（有的返回 `Result<T>`，有的返回裸 `ResponseEntity`） | 统一使用 `ApiResponse<T>` 包装，`@RestControllerAdvice` 统一处理 |
| 分页参数各有各的写法 | 统一使用 `PageQuery` 基类 + `PageResult<T>` 返回 |

#### 3.1.3 异常处理标准化

| 现状问题 | 重构方案 |
|----------|----------|
| 业务异常直接 `throw new RuntimeException("xxx")` | 定义 `BusinessException` + 错误码枚举 `ErrorCode` |
| 部分 Service 吞异常返回 null/空列表 | 该抛就抛，由 `GlobalExceptionHandler` 统一转换为标准错误响应 |
| `try-catch` 散落各处 | 收敛到 AOP 切面（`@ExceptionHandler` 已在 ControllerAdvice，确保所有异常都到达该层） |

**统一错误码体系**：
```
USER_NOT_FOUND(1001, "用户不存在"),
INSUFFICIENT_STOCK(2001, "库存不足"),
DOCUMENT_NOT_FOUND(3001, "单据不存在"),
AI_PROVIDER_ERROR(4001, "AI 服务暂不可用"),
...
```

#### 3.1.4 日志规范统一

| 现状问题 | 重构方案 |
|----------|----------|
| `System.out.println()` 散落 | 全局搜索删除，全部改为 SLF4J |
| 日志级别混乱（`log.info` 打印异常堆栈） | 规范：`ERROR`=需要人工介入 / `WARN`=可自动恢复的异常 / `INFO`=关键业务节点 / `DEBUG`=开发调试 |
| 日志无 traceId | 引入 MDC traceId（Filter 注入，全链路携带） |
| 敏感信息可能泄露 | 日志脱敏：手机号/邮箱/密码/API Key 自动掩码 |

#### 3.1.5 代码重复消除

| 重复模式 | 统一方案 |
|----------|----------|
| 分页转换逻辑（各 Service 重复 `Page<Entity> → PageResult<DTO>` | 抽取 `PageUtils.toPageResult(page, converter)` |
| 日期格式化 `SimpleDateFormat` 到处 new | 统一 `DateUtils` 工具类（线程安全） |
| 库存校验逻辑（入库出库都重复检查库存是否足够） | 抽取 `InventoryValidator` |
| 权限检查散落各 Controller | 统一用 `@PreAuthorize` + `PermissionEvaluator` |
| Excel/CSV 导出逻辑 | 抽取 `ExportUtils` |

#### 3.1.6 单元测试补全

> **目标**：核心 Service 覆盖率 ≥ 60%。

| 模块 | 优先级 | 测试重点 |
|------|--------|----------|
| `InventoryService` 拆解后的各子 Service | P0 | 入库/出库/盘点核心逻辑、库存不足边界 |
| `AiService` 拆解后的 Provider 路由 | P0 | Provider 选择、降级逻辑、流式/非流式分支 |
| `TicketService` | P1 | 工单状态流转、沉淀知识逻辑 |
| `PurchaseService` / `SalesService` | P1 | 审核流程、应收应付计算 |
| `Function Calling` 工具函数 | P1 | 参数校验、权限检查、无结果返回 |

**测试框架**：JUnit 5 + Mockito + AssertJ
**测试数据库**：H2 内存数据库（单元测试）/ Testcontainers MySQL（集成测试）
**CI 要求**：`mvn test` 必须在 CI 中执行，覆盖率报告用 JaCoCo 生成。

#### 3.1.7 去除无用代码

- 全局搜索 `@Deprecated` 注解，确认是否可安全删除
- 删除从未被调用的 `public` 方法（IDE 静态分析 + 人工确认）
- 删除注释掉的大段代码块（Git 历史可追溯，无需保留在源码中）
- 删除未被使用的 DTO/VO 类
- 删除未使用的 import

### 3.2 前端重构（第 2-4 周）

#### 3.2.1 大组件拆分

> **目标**：每个 `.vue` 文件 ≤ 250 行（不含样式），组件树清晰。

| 需要拆分的组件（预估） | 现状行数 | 拆分方案 |
|------------------------|----------|----------|

#### 3.2.2 通用组件抽取

| 重复 UI 模式 | 统一组件 |
|-------------|----------|
| 表格 + 分页 + 搜索 + 导出 | `<DataTable>` 统一组件（props 驱动） |

| 表单抽屉（新增/编辑） | `<FormDrawer>` 统一打开/关闭/提交/重置 |

#### 3.2.3 TypeScript 类型安全提升

| 现状问题 | 重构方案 |
|----------|----------|
| `any` 类型泛滥 | 遍历所有 `any`，逐一替换为具体类型或 `unknown` + 类型守卫 |
| API 响应类型不完整 | 为所有后端 API 响应定义完整 TypeScript 接口 |
| `as` 强制类型断言过多 | 用类型守卫替换 `as`，运行时安全 |
| `tsconfig.json` `strict: false` | 逐步启用 `strict: true`（分模块渐进式） |

#### 3.2.4 工具函数统一

| 重复函数 | 统一方案 |
|----------|----------|
| `formatDate()` 各页面自行实现 | 统一到 `@/utils/date.ts` |
| `downloadFile()` / `exportCsv()` | 统一到 `@/utils/export.ts` |
| `confirmDialog()` 各页面重复 | 统一到 `@/composables/useConfirm.ts` |
| 分页 `page`/`pageSize` 状态管理 | 统一到 `@/composables/usePagination.ts` |
| 权限判断 `canEdit` / `canDelete` | 统一到 `@/composables/usePermission.ts` |
| API 请求错误处理 | 统一在 `@/utils/request.ts` 拦截器中处理 |

| E2E 扩展 | 从 10 条扩展到 ≥ 25 条，覆盖角色边界、并发、边界值 |

#### 3.2.6 性能优化

### 3.3 基础设施加固（第 3-4 周）

#### 3.3.1 Docker 镜像优化

| 优化项 | 方案 |
|--------|------|
| 后端分层构建 | 先 copy `pom.xml` → `mvn dependency:resolve`（利用 Docker 缓存层）→ 再 copy 源码 `mvn package` |
| 前端多阶段构建 | `node:20-alpine` 构建 + `nginx:1.27-alpine` 运行，最终镜像不含 node_modules |
| 基础镜像版本锁定 | 所有 Dockerfile 使用精确版本号 `node:20.18-alpine`，禁止 `latest` |
| `.dockerignore` 完善 | 排除 `node_modules`, `.git`, `tests`, `docs`, `*.md` |
| 健康检查完善 | 所有容器添加 `HEALTHCHECK` 指令 |

#### 3.3.2 CI 稳定性

| 优化项 | 方案 |
|--------|------|
| MySQL/Redis 容器启动等待 | 使用 `wait-for-it.sh` 或 Docker healthcheck 依赖 |
| npm install 缓存 | CI 中配置 `~/.npm` 缓存目录 |
| Maven 依赖缓存 | CI 中配置 `~/.m2` 缓存目录 |
| 超时时间调整 | 合理设置每个 step 的 timeout（避免挂死） |
| 重试机制 | 对网络相关的 step（npm install、mvn dependency）加自动重试 2 次 |

#### 3.3.3 代码静态分析

| 工具 | 用途 |
|------|------|
| ESLint (前端) | 启用 `@typescript-eslint/no-explicit-any` 规则，逐步消除 `any` |
| Prettier (前端) | 统一格式化，CI 中 `--check` |
| Checkstyle / SpotBugs (后端) | 代码规范 + 潜在 bug 检测 |
| SonarQube (可选) | 代码质量门禁（复杂度过高、重复率过高自动拦截） |

#### 3.3.4 环境变量和配置审计

| 检查项 | 说明 |
|--------|------|
| 环境变量完整性 | 检查 `.env.example` 是否包含所有 `application.yml` 中引用的环境变量 |
| 敏感信息泄露检查 | 确保所有密码/密钥来自环境变量，不在代码或配置文件中硬编码 |
| 默认值安全性 | 所有配置项必须有安全的默认值（dev 环境可宽松，prod 必须严格） |

## 6. 不涉及（严格禁止）

1. **禁止新增业务功能** — 任何产品需求推迟到 v1.4 / v2.0

6. **禁止引入新的第三方依赖** — 除非是测试/静态分析工具且无替代方案
7. **禁止跨模块大规模改动** — 一次只重构一个模块，确保 git bisect 可用

## 8. 验收标准

### 代码质量
1. 后端核心 Service 单元测试覆盖率 ≥ 60%（JaCoCo 报告）。
2. 前端通用组件测试覆盖率 ≥ 50%（Vitest 报告）。
3. TypeScript `strict: true` 零编译错误。
4. 所有 `any` 消除或标注了合理的 `@typescript-eslint/no-explicit-any` 注释（注释需解释原因）。
5. 后端零 `System.out.println()`。
6. 所有异常通过 `BusinessException` + `ErrorCode` 枚举抛出，由 `GlobalExceptionHandler` 统一处理。
7. 所有 SLF4J 日志按规范级别输出，敏感信息已脱敏。
8. 复制粘贴检测（CPD）重复率 < 5%。

### 架构
9. 后端 Service 单类 ≤ 300 行。
10. 前端组件单文件 ≤ 250 行（不含 `<style>`）。
11. 通用组件（DataTable / StatusBadge 等）所有使用处替换完成，旧代码已删除。

### 稳定性
12. CI 连续 10 次全绿不重试。
13. Docker 构建时间减少 ≥ 30%。
14. Docker 前端镜像 < 50MB，后端镜像 < 300MB。
15. `mvn test` 全量通过（含新增单元测试）。
16. `npm run test:e2e` ≥ 25 条全量通过。

### 兼容性
17. v1.2 所有 API 响应格式不变（E2E 验证）。
18. v1.2 所有页面功能行为不变（手动冒烟）。
19. `docker compose up` 一键启动无报错。
20. `reset-commercial-baseline.ps1` 执行通过。
21. `data-quality-check.ps1` 执行通过。

## 9. 风险与应对

| 风险 | 应对 |
|------|------|
| 重构引入回归 bug | 先写测试再重构；每重构一个模块立即跑该模块测试 + E2E 全量 |
| TypeScript strict 开启导致编译大面积报错 | 通过 `tsconfig.json` 的 `exclude` 渐进式开启，先 types/utils → composables → components → views |
| 大组件拆分后 props/events 传递复杂 | 需要拆分的组件优先用 `provide/inject` 或 composable 替代 props drilling |
| 单元测试编写耗时超出预期 | 优先覆盖 P0 模块（Inventory / AI Provider 路由），P1 模块可适度简化 |
| Docker 构建优化后行为不一致 | 构建后跑 E2E 全量验证；`docker compose up` 冒烟 |
| 团队对"不新增功能"有分歧 | 严格按本文档第 6 节执行，任何功能需求记录到 v1.4 backlog |

### 回滚策略
- 所有重构在独立分支 `develop/v1.3` 上进行。
- 合并到 `main` 前需全量 E2E 通过。
- 如有重大问题，可放弃该分支基于 v1.2 重新来过（因为逻辑上等价）。
